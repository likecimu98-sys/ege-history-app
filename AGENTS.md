## Что это за проект
PWA-тренажёр для подготовки к ЕГЭ по истории (ваниль JS, без сборщика для JS; CSS — Tailwind
в `output.css`). Прод: **https://reshay-istoriyu.ru**. Клиент — Telegram Mini App
(@Reshay_istoriyu_bot), большинство пользователей **на мобильном**.

## Архитектура (после миграции Firebase→PostgreSQL, июль 2026)
- **CDN: основной домен стоит ЗА Cloudflare (с 2026-07-22).** Домен `reshay-istoriyu.ru` (регистратор
  REG.RU) делегирован на NS `demi.ns.cloudflare.com` / `melnicoff.ns.cloudflare.com`; A-записи
  root (Proxied) ведут на origin `185.198.152.200`. `www.reshay-istoriyu.ru` с 27.07
  намеренно оставлен DNS-only на тот же IP как диагностический/аварийный прямой маршрут;
  клиент на `www` снимает старые Service Worker и новый не ставит. Причина: «не открывается на части
  устройств / ERR_TIMED_OUT» после миграции оказалось нестабильной сетевой достижимостью
  ОДНОГО голого IP (запросы не доходили до nginx вовсе); CDN с anycast-IP это вылечил —
  проверено на реальных застрявших устройствах. НЕ отключай проксирование (серые облачка)
  у ОСНОВНОГО домена без явного решения пользователя. Прямой `www` — не гарантия доступности:
  он как раз показывает, достигается ли голый IP из сети ученика. Настройки CF: SSL **Full**, WebSockets On, Browser Cache
  TTL = Respect Existing Headers (наши `no-cache` уважаются, `cf-cache-status: DYNAMIC/MISS`).
  Следствия: в nginx access.log клиентские IP теперь Cloudflare (162.158.x/172.70.x и др.) —
  РЕАЛЬНЫЙ IP бери из первой записи `X-Forwarded-For` (API так и делает: `trustProxy=true`,
  рейт-лимит считает по реальным IP — не «чини» это). TODO по желанию: nginx real_ip
  (`CF-Connecting-IP`) для красивых логов; фаервол «80/443 только с IP Cloudflare» — ТОЛЬКО
  вместе с Cloudflare Origin Certificate (иначе сломается продление Let's Encrypt).
- **Хостинг (origin):** VPS `185.198.152.200` (root), Nginx `root /var/www/ege-app` (обычная папка),
  Let's Encrypt. `location /auth/` проксируется в API. Конфиг сайта:
  `/etc/nginx/sites-enabled/reshay-istoriyu.ru`.
- **Данные/синк:** PostgreSQL на VPS (миграция с Firebase завершена). Клиентские модули синка —
  `cloud-sync.js` + `vps-sync-compat.js`. Старый `firebase-sync.js` выведен из клиента и
  **не должен попадать в прод-архив** (`.gitattributes export-ignore`).
- **Бот:** `/root/bot/` на VPS (pm2). API/инфра: `/opt/ege-history-api`, `/opt/ege-history-infra`.
- **Кэш клиента:** Service Worker с версией `APP_VERSION` в `service-worker.js`
  (формат сейчас `2026-07-DD-vps-N`). **Меняешь кэшируемый JS/HTML/CSS — обязательно подними
  версию SW и общий `?v=RELEASE` всех стартовых JS/CSS**, иначе старый worker может собрать
  новый HTML со старыми файлами. Запись ответа в CacheStorage не должна блокировать выдачу
  сетевого ответа странице. В Telegram на iOS Service Worker намеренно отключён из-за
  зависаний WKWebView CacheStorage; обычная PWA в Safari остаётся офлайн.

## ДЕПЛОЙ — читай внимательно, тут была главная путаница
- **Рутинный деплой сайта → `powershell -File deploy-static.ps1`.**
  git archive HEAD → scp → распаковка в `/var/www/ege-app.release-*` с атомарной заменой
  symlink `/var/www/ege-app`. Перед переключением создаётся однокомандный откат на точный
  предыдущий релиз: `bash /root/ege-app-static-rollback.sh`. Хранятся три релиза. Внешняя
  проверка делает до трёх попыток и не объявляет успех при не-200. **Базу данных не трогает.**
  Это правильный скрипт для обычных правок.
- **Деплой серверного API → `powershell -File deploy-api.ps1`** (создан 26.07.2026).
  `git archive HEAD:server/api` → scp → `npm ci --omit=dev` → `node --test` НА СЕРВЕРЕ →
  атомарная замена `/opt/ege-history-api` → `pm2 restart hist-api` → health-check
  `127.0.0.1:8792/api/v1/health` 20 секунд → **автоматический откат, если не ответил**.
  Снимки `ege-history-api.prev-*` (хранятся три). БД, миграции и `/etc/ege-history/api.env`
  не трогает — миграции гоняются отдельно (`npm run migrate` в server/api).
  ⚠️ **Правку API руками на боевом сервере не делай.** Именно так `src/auth.js` разошёлся
  с репозиторием на сутки и остался бы миной под любым будущим деплоем. Нужна срочная
  правка — делай в репозитории и гони скриптом; он быстрее ручного scp и умеет откат.
  ⚠️ Удалённая часть едет **файлом** (scp + `bash`), а не аргументом ssh: PowerShell 5.1
  корёжит вложенные кавычки, а в скрипте есть sed/curl со своими кавычками.
- **`deploy-vps.ps1` — это РАЗОВЫЙ cutover Firebase→PostgreSQL, НЕ рутинный деплой.**
  С `-Cutover -ConfirmCutover RESHAY_HISTORY_VPS` он **переключает боевую БД**, импортирует
  Firestore, ставит окна отката. **Не запускай его для правок сайта.** Cutover уже выполнен.
  Его снимки отката `ege-app.rollback-*` / `*.client-rollback-*` — 60-дневная страховка,
  их удалять/трогать нельзя.
- **SSH:** строгая проверка host key (`StrictHostKeyChecking=yes`, только `ssh-ed25519`,
  ключ `~/.ssh/id_ed25519`). Отпечаток сервера:
  `SHA256:2QvI08yVRpFJ4D35RElDDHmPBoMl88u9+qT0AhNcVKs`. **Не отключай строгую проверку и не
  делай `ssh-keyscan`** — это обесценит пиннинг.
- **Профиль Windows с пробелом** («Хозяин Саша») ломает путь `UserKnownHostsFile` в ssh.
  Оба .ps1 используют **DOS 8.3-короткие пути** (`C:\Users\90DF~1\...`). PowerShell 5.1 корёжит
  встроенные кавычки при передаче в native ssh/scp — поэтому именно короткие пути, не кавычки.
- **.ps1 — только ASCII** (PowerShell 5.1 читает скрипты в ANSI без BOM; кириллица → парс-ошибки).
- `deploy-static.ps1` после распаковки нормализует mtime файлов по часам VPS: локальные часы
  могут быть впереди сервера, а будущий `Last-Modified` ломает браузерную ревалидацию кэша.
- После деплоя: `git push origin master` (GitHub — запасной адрес/бэкап).

## Что на самом деле защищает дневной лимит (читать до разговора о деньгах)
Лимит строк с 26.07.2026 считает сервер: таблица `usage_counters`, эндпоинты
`GET /api/v1/quota` и `POST /api/v1/quota/consume`, день по **Europe/Moscow**
(иначе лимит добирается переводом часов на телефоне). Клиентская `canSolveMore()`
осталась синхронной и читает снимок ответа — её зовут прямо из `checkAnswers`.

**Граница защиты, не обманывайся ею.** Весь контент (`data.js`,
`exam-bank.generated.js`) уже лежит в браузере, а «я решил N строк» и «сейчас идёт
домашка» — утверждения КЛИЕНТА. Сервер держит источником правды сам тариф
(премиум, безлимит класса, роль) и закрывает обход «в один клик» из DevTools, но
не мешает тому, кто правит JS.
⇒ **Подписку нельзя продавать как «больше строк в день».** Продавать надо то, что
физически живёт на сервере (проверка второй части ЕГЭ, кабинет учителя, банк за
эндпоинтом). Это продуктовое решение — задача 3.1 плана, решает пользователь.
⚠️ Признак `premium` читается из документа ученика, а свой документ ученик пишет
целиком. Когда появятся настоящие платежи, источником правды обязана стать
таблица подписок, а не флаг в профиле.

## Инварианты — НЕ ломать без явного согласия пользователя
- Безопасность деплоя: строгий host key + ed25519-пиннинг (см. выше).
- Прод-архив НЕ содержит `server/`, `firebase-sync.js` (гарды в обоих .ps1 — сохраняй их).
- Firestore/доступы, дневные лимиты строк, ролевые правила учителей — менять только по задаче.
- Тема: в приложении оставлена ТОЛЬКО `skin-classic` (пикер тем удалён). Другие скины в
  `theme-aurora.css` — мёртвый груз, но `body.skin-classic` активна всегда; правя чипы/цвета,
  проверяй И светлую, И тёмную тему (`html.dark`).
- **iOS/кэш — инварианты против «белого экрана на айфонах» (стоили нам недели):**
  1. **Nginx отдаёт `index.html` и весь JS/CSS с `Cache-Control: no-cache`** (`location /`).
     Без него iOS WKWebView кэширует вход эвристически (только `Last-Modified`) и НЕ ходит за
     обновлениями — новые деплои не доезжают до айфонов. Долгий кэш — только у картинок/медиа/
     шрифтов (отдельный `location ~*`). SW и манифест — тоже `no-cache`. НЕ убирай эти заголовки.
  2. **Service Worker НИКОГДА не завязывает ответ страницы на CacheStorage.** На iOS
     `cache.match`/`cache.put` под нагрузкой (20 defer-скриптов) сериализуются и могут не
     ответить → `respondWith` висит → белый экран навсегда. Правило: чтение кэша — под таймаутом
     (`CACHE_READ_TIMEOUT_MS`), запись — только фоновая (`waitUntil`/fire-and-forget), install не
     блокирует активацию на кэшировании. НЕ возвращай `await cache.put(...)` на путь ответа.
  3. **Экран «Загрузка задержалась» НЕ прекращает проверку готовности ядра.** Медленная сеть
     может честно довезти последний defer-скрипт после 12 секунд. `watchBoot()` обязан продолжать
     опрос и снять заставку при появлении `quickStartGame`; иначе уже рабочее приложение навсегда
     остаётся под оверлеем. Это исполняется тестом `slowCoreStillDismissesRecoveryScreen`.
  4. **`/sw-recover` намеренно отвечает HTTP 418 с полноценным HTML, это НЕ ошибка.**
     Установленный до iPhone-фиксов worker ждёт `cache.put()` перед возвратом любого успешного
     (`response.ok`) ответа и при сломанном CacheStorage не даёт новому HTML выполниться вообще.
     На 418 его `putIfOk()` не пишет в кэш и сразу отдаёт автономную страницу восстановления.
     Не меняй ответ на 200 и не добавляй ей внешние JS/CSS. Она удаляет только регистрации SW
     и кэши `ege-history-*`, но не `localStorage`, IndexedDB, cookies, аккаунт или прогресс.
     В Telegram после `unregister()` НЕЛЬЗЯ редиректить это же окно на `/`: активный старый
     worker продолжает контролировать уже открытый WebView до его уничтожения и снова перехватит
     переход. Recovery вызывает `web_app_ready`, затем `web_app_close`; ученик открывает новый
     WebView второй кнопкой из ответа `/repair`. В обычном браузере автоматический редирект остаётся.
  5. **Вторая кнопка `/repair` обязана открывать ДРУГОЙ origin**
     `https://www.reshay-istoriyu.ru/?recovery=1`, а не основной домен. Регистрация Service Worker
     хранится между Telegram WebView, поэтому даже новое окно на основном домене снова попадает
     под старый зависший worker, если `getRegistrations()` завис и не смог его удалить. На `www`
     этот worker не существует, новый SW там намеренно не устанавливается, а API принимает origin
     `www` через `EXTRA_ORIGINS`. Старые сообщения бота неизменяемы: после правки кнопки ученик
     должен заново отправить `/repair`.

## Правила работы с данными и контентом (тихие потери, которые не видно глазом)
Перенесено 27.07.2026 из `AI_BRIEFING.md` — он описывал уже несуществующий Firebase-мир
и звал деплоить через `deploy-vps.ps1`, поэтому удалён. Здесь только то, что осталось верным.

1. **Учитель НИКОГДА не переписывает `fullStateJson` ученика.** Блоб прогресса пишет только
   сам ученик при синхронизации. Учительские действия (выдача/отмена ДЗ, выпуск из класса) —
   через отдельные верхнеуровневые поля, перечисленные в `TEACHER_STUDENT_WRITE_FIELDS`
   (`server/api/src/store.js`). Чтение-модификация-запись чужого блоба = гонка и затирание.
2. **Новое поле в `state.stats`, которое должно жить в облаке, регистрируется в ЧЕТЫРЁХ местах:**
   инициализация в `state.js`, `SAVE_FIELDS` (`state.js`), merge-логика `deepMergeStates`
   и `CLOUD_STATE_FIELDS` (оба — `cloud-sync.js`). Пропустишь одно — поле тихо теряется при
   слиянии устройств, и заметят это через недели.
3. **Новый аккаунт-зависимый ключ `localStorage` → сразу в `IDENTITY_WIPE_KEYS`**
   (`cloud-sync.js`). Иначе смена аккаунта на общем ПК смешает прогресс двух разных людей.
4. **Проверка «двойного ответа» в заданиях не может опираться только на скрипт-оракул по базе** —
   он не ловит смысловые пересечения. Пример, пойманный руками: «Тройка передвижников» и
   «Иван-царевич на сером волке» Васнецова засчитывались как два верных ответа, пока не были
   связаны через `appliesToIds`/`GROUPS` в `unifyTask7Applies` (`state.js`). Меняешь генератор
   заданий — перечитывай реальные сгенерированные таблицы, а не только вывод скрипта.
5. **Тяжёлые данные (`visual*Data.generated.js`) не возвращать в `defer`-цепочку `index.html`
   и в прекэш SW** — они грузятся лениво в фоне ради первой загрузки на мобильных.
6. **Задание 5 ЕГЭ официально включает участников СВО** — это экзаменационный материал, а не
   позиция автора. Строить по нему нейтральные тренажёры нормально, отказывать не нужно.
7. **Главная кнопка лобби** — `computeMainAction()` (`ui.js`): лестница ДЗ → ротация
   (новое/ошибки/повтор) → слабое место → «всё выучено». Правки сюда меняют то, что видит
   каждый ученик при каждом входе.

- Крупные/необратимые действия (переключение БД, миграции, удаление данных, смена настроек
  сервера) — только с явного «да» пользователя.
- **Задеплоил — сразу поправь статус в журнале.** Записи за 26 и 27 июля висели с пометкой
  «НЕ ЗАДЕПЛОЕНО» уже после выката: их пишут перед деплоем и забывают обновить. Следующий
  агент по такому журналу либо выкатит второй раз, либо начнёт «чинить» уже рабочее.
