## 2. Правила работы — нарушать нельзя

1. **Рутинный деплой** — `powershell -File deploy-static.ps1`. `deploy-vps.ps1` **не
   запускать никогда** (это разовый cutover БД, он уже выполнен).
2. **Меняешь кэшируемый JS/HTML/CSS** — подними `APP_VERSION` в `service-worker.js`
   и общий `?v=RELEASE` у всех стартовых файлов в `index.html` (+ внутри
   `cloud-sync.js` для `vps-sync-compat.js`, он легко теряется).
3. **Перед деплоем** — `npm run check` (SW-selftest + design-lint) и
   `cd server/api && node --test test/*.test.js`. Всё зелёное или не деплоишь.
4. **UI проверяй на 375px** в светлой и тёмной теме — это целевая среда.
5. **iOS-инварианты** (стоили проекту недели, описаны в AGENTS.md): Nginx отдаёт
   HTML/JS/CSS с `Cache-Control: no-cache`; Service Worker никогда не завязывает
   ответ страницы на CacheStorage. Не трогай.
6. **Правки боевого API/nginx/бота** — только с бэкапом рядом
   (`/root/<file>.<дата>.bak`), `nginx -t` перед reload, `pm2 restart` после.
7. **Необратимое** (миграции, удаление данных, смена тарифов, публикация оферты) —
   только после явного «да» пользователя.
8. Коммиты на русском с префиксом `fix/feat/chore(область)`. Ветка `master`.
   Force-push запрещён.
9. **В конце этапа обнови «Журнал передачи» в AGENTS.md** — что сделал, почему,
   какие ловушки нашёл.

### Особое требование этого плана

Мы чиним доступ к персональным данным несовершеннолетних. Любая правка прав
доступа сопровождается **регрессионным тестом в `server/api/test/`**. Тест без
правки бесполезен, правка без теста не принимается.

### Задача 1.1. Закрыть утечку реестра учеников 🔴

**Проблема.** Любой посетитель (клиент сам заводит гостевую сессию при открытии
сайта) одним запросом получает список всех учеников с ФИО, Telegram-@username и
кодом класса.

**Доказательство** (воспроизводится в консоли браузера на проде, свежая вкладка):

```js
await (await fetch('/api/v1/store/query', {
  method:'POST', headers:{'content-type':'application/json'}, credentials:'include',
  body: JSON.stringify({path:'artifacts/ege-history-bot/public/data/students',
                        constraints:[{type:'limit',count:5000}]})
})).json()
// → 200, docs.length === 1201, поля: name, username, classCode, totalSolved, lastActive
```

**Корень:** `server/api/src/store.js`, `authorizeRead`, ветка `case 'students'` —
при `query:true` посторонняя строка возвращается как «публичная» вместо отказа.
Плюс `case 'classes' / 'matches' / 'leaderboards'` отдают `{ok:true, full:true}`
любой сессии.

**Что сделать.**

1. `authorizeRead`, `students`: убрать `return query ? {ok:true, full:false} : {ok:false}`
   — посторонний не получает строку ни в каком режиме.
2. `classes`: читать может только учитель, у которого этот `classCode` в
   `ctx.classes` (или админ). Совпадает с логикой `authorizeWrite`.
3. `matches`: полный документ — только участникам (`ownMatchActor`) и админу.
   Для матчмейкинга добавить проекцию `publicMatch(data)`: `status`, `mode`,
   `createdAt`, `swipeSections` и по игрокам только `{name, elo}` — **без `uid`**
   (сейчас `uid` = Telegram ID, это утечка).
   ⚠️ Проверь `match-mode.js` и `cloud-sync.js:884..1200`: клиент опознаёт «мой
   матч» по `player.uid`. Для списка ожидания это не нужно, для открытого матча
   документ отдаётся полностью — там `uid` останется.
4. `leaderboards`: оставить читаемым, но заполнять его **только сервером**
   (запись уже запрещена в `authorizeWrite`).
5. Ввести серверный эндпоинт `GET /api/v1/leaderboards` как **единственный**
   публичный источник рейтинга. Реализовать на SQL с `ORDER BY ... LIMIT`,
   используя существующие индексы `student_profiles_total_idx` (см. задачу 2.1),
   а не через `store.query`. Проекция строки: `{ rank, displayName, egePoints,
   weeklyScore, duelRating }`, где `displayName` — **имя + первая буква фамилии**
   («Иван П.»). Ни `username`, ни `classCode`, ни `doc_id` наружу не уходят.
6. Клиент: заменить все прямые запросы коллекции `students` на серверные
   эндпоинты. Карта мест — Приложение А. Флоу «найти ученика по googleEmail»
   (`cloud-sync.js:3511`) вынести в серверный эндпоинт связывания аккаунтов —
   поиск по чужому email из браузера существовать не должен.
7. Проверить WebSocket: подписка на коллекцию (`server.js`, ветка
   `segments.length === 5`) разрешает подписаться на `students` и получать поток
   изменений с путями = Telegram ID. Разрешить подписку на коллекцию только
   учителю/админу; ученику — только на свои документы и свои матчи.

**Критерий приёмки.**
- Проба выше от гостевой сессии → `403`.
- Новые тесты в `server/api/test/store-access.test.js`: гость не читает чужой
  профиль (get и query), учитель не читает ученика чужого класса, учитель читает
  своего, админ читает всех, участник дуэли читает свой матч, посторонний видит
  матч без `uid`.
- Лидерборд, глобальный топ, кабинет учителя, ДЗ, дуэли, связывание Google — вручную
  проверены на проде после деплоя. Это самая рискованная задача плана: у клиента
  13+ мест обращения к `students`, и молчаливая поломка кабинета учителя дороже
  самой утечки.

**Не делать.** Не ломай `internal:true`-путь (бот пишет через него). Не трогай
`protectTeacherClassAssignment` — это защита учительского приглашения.

### Задача 1.2. Перенести дневной лимит и premium-гейт на сервер 🔴

**Проблема.** `state.js:484 canSolveMore()` считает лимит по локальному состоянию
ученика. Правится из DevTools за десять секунд. Платный контур обходится тривиально.

**Что сделать.**

1. Таблица `usage_counters(user_id, day date, kind text, count int, PRIMARY KEY(user_id,day,kind))`,
   новая миграция `003_usage_counters.sql`.
2. `GET /api/v1/quota` → `{limit, used, left, premium, resetAt}`. Источник лимита —
   `app_config/limits` (`freeDaily` / `premiumDaily`, 0 = безлимит), `premium` —
   `student_profiles.data.premium || premiumAuto`. Ученик на своё значение влиять
   не может.
3. `POST /api/v1/quota/consume {kind:'lines', amount:N}` → атомарный
   `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, при исчерпании — `429` с
   `{error:'daily_limit_reached', resetAt}`. Требует CSRF (как все мутации).
4. Клиент: `canSolveMore()` спрашивает сервер (с локальным оптимистичным кэшем на
   время раунда), при `429` показывает существующий экран лимита.
5. **Освободить от лимита** те же категории, что и сейчас: ДЗ, дуэли, учителя,
   классы с безлимитом. Проверь текущие исключения перед правкой, не потеряй их.

**Честное ограничение, зафиксируй его в AGENTS.md.** Весь контент (`data.js`,
`exam-bank.generated.js`) уже лежит в браузере. Серверный лимит закрывает обход «в
один клик», но не защищает от того, кто правит JS. **Поэтому подписка не должна
продаваться как «больше строк в день».** Продавать надо то, что физически живёт на
сервере (см. задачу 3.1) — это продуктовое решение, вынеси его пользователю
отдельным вопросом, не решай сам.

**Критерий приёмки.** Правка `localStorage`/`window.state` не увеличивает число
доступных строк. `GET /api/v1/quota` после N решённых строк показывает `used = N`.
Тест на атомарность счётчика при параллельных `consume`.

### Задача 1.3. Заголовки безопасности и внешний CDN 🔴

**Проблема.** Ответ прода не содержит ни одного заголовка безопасности:
нет `Content-Security-Policy`, `Strict-Transport-Security`, `frame-ancestors`,
`X-Content-Type-Options`, `Permissions-Policy`. При этом `ege_csrf` намеренно
`httpOnly:false`, в `ui.js:2484` имя класса подставляется в `<option>` без
экранирования, а `jsPDF` подгружается с `cdnjs.cloudflare.com` без SRI
(`cloud-sync.js:1853` и `:1985`) — то есть внешний скрипт исполняется с полными
правами страницы.

**Что сделать.**

1. **Завести конфиг сайта в git**: скопируй боевой
   `/etc/nginx/sites-enabled/reshay-istoriyu.ru` в `server/infra/nginx-site.conf`
   (он уже `export-ignore`, в прод-архив не попадёт). Сейчас его нет в репозитории
   вообще — это дыра в восстановлении.
2. Добавить в `location /`:
   ```
   add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
   add_header X-Content-Type-Options "nosniff" always;
   add_header Referrer-Policy "strict-origin-when-cross-origin" always;
   add_header Permissions-Policy "geolocation=(), microphone=(), camera=(), payment=()" always;
   add_header Content-Security-Policy "<см. ниже>" always;
   ```
   ⚠️ В nginx `add_header` в вложенном блоке **отменяет** заголовки родителя —
   проверь, что `Cache-Control: no-cache` из iOS-инварианта не потерялся. Это
   ровно тот случай, когда «мимоходом» ломают неделю работы.
3. Стартовый CSP (в проекте нет `eval`, но есть инлайновые `<script>` в
   `index.html`, поэтому `'unsafe-inline'` пока остаётся):
   ```
   default-src 'self';
   script-src 'self' 'unsafe-inline';
   style-src 'self' 'unsafe-inline';
   img-src 'self' data: blob:;
   font-src 'self';
   connect-src 'self';
   frame-src https://yandex.ru https://*.yandex.ru;
   frame-ancestors 'self' https://web.telegram.org https://*.telegram.org https://telegram.org;
   base-uri 'none'; form-action 'self'; object-src 'none'
   ```
   `frame-ancestors` **обязан** пускать Telegram, иначе мини-апп в браузерном
   Telegram превратится в белый экран. Выкатывай сначала как
   `Content-Security-Policy-Report-Only` на сутки, собери нарушения, потом включай.
4. **Самохостить jsPDF**: положить `jspdf.umd.min.js` в `vendor/`, грузить с
   своего origin (как уже сделано с `telegram-web-app.js` — там ровно тот же довод:
   внешний домен часто недоступен у части аудитории). Обе функции экспорта PDF
   перевести на локальную копию, внешний URL удалить.
5. Починить `ui.js:2484` — экранировать `g.name` (в проекте уже есть `escapeHtml`
   в `modes.js:166`). Заодно прогони остальные 146 присваиваний `innerHTML` на
   предмет подстановки пользовательских строк; интересуют имена, названия классов
   и всё, что приходит из БД.

**Критерий приёмки.** `curl -sI https://reshay-istoriyu.ru/` показывает все пять
заголовков и по-прежнему `cache-control: no-cache`. Мини-апп открывается в
Telegram на iOS и Android и в браузерном Telegram. Экспорт PDF работает при
заблокированном `cdnjs`. В консоли нет CSP-нарушений.

5. Подготовить пользователю чек-лист того, что агент сделать не может:
   уведомление в РКН, статус ИП/самозанятого, договор с платёжным провайдером,
   реквизиты в оферте, возрастная маркировка.

**Критерий приёмки.** Документы открываются, согласие сохраняется и переживает
переустановку, удаление аккаунта реально стирает строки (проверено SQL-запросом),
`npm run check` зелёный.

### Задача 2.1. Убрать full table scan из хранилища 🟠

**Проблема.** `store.js` `query()` делает `SELECT doc_id,user_id,data,version FROM
<table>` **без `WHERE` и `LIMIT`**, затем фильтрует, сортирует и режет в JS, а права
проверяет построчно. Индексы `student_profiles_class_idx` и `student_profiles_total_idx`
созданы в миграции и не используются никогда.

**Замер на проде:** запрос по 1201 строке — 928 мс (из них ~500 мс серверной
работы в однопоточном Node). На 5000 учеников это ~2 с блокировки event loop на
каждый такой запрос.

**Что сделать.** Транслировать `constraints` в SQL: `where` → `data->>'field' = $n`
(для `classCode` попадёт в существующий индекс), `orderBy` → `ORDER BY`, `limit` →
`LIMIT`. Сохранить текущую семантику (сравнение как в `filterValue`, `null` в
конце сортировки — сейчас так). Предварительно сузить выборку правами: для учителя
— `WHERE data->>'classCode' = ANY($classes)`, для ученика — свои `doc_id`.
Не тащить `data` целиком там, где нужны 5 полей: у профилей внутри лежит
`fullStateJson` на сотни килобайт.

**Критерий приёмки.** `EXPLAIN ANALYZE` показывает Index Scan, а не Seq Scan.
Тот же запрос от учителя — меньше 100 мс. Существующие тесты
`store-primitives.test.js` зелёные, добавлены тесты на трансляцию constraints.

### Задача 2.2. Сократить холодный старт 🟠

**Замер на проде** (гость, ноль действий пользователя): **25 обращений к API**, из
них 5 × `store/query` (те самые полные сканы), 6 одинаковых чтений своего же
документа, 4 записи и **4 запроса `/api/v1/teacher/classes`, которые заведомо
вернут 403**.

При рейт-лимите 300/мин **на IP** класс из 25 человек за одним школьным NAT
выжигает лимит на входе. Это тот же механизм, который уже сработал 23.07 в кабинете
учителя.

**Что сделать.**
1. Один composite-эндпоинт `GET /api/v1/bootstrap` → профиль + состояние + квота +
   лимиты + роль + ДЗ одним ответом.
2. Не спрашивать `/teacher/classes` у гостя вовсе, и не повторять запрос после 403
   в пределах сессии.
3. Дедуплицировать чтения одного и того же документа (промис-кэш на время загрузки).
4. Рейт-лимит считать по паре «сессия + IP», для IP оставить только грубый потолок
   от ботов. Сейчас `MemoryRateLimiter` живёт в памяти одного процесса — если
   когда-нибудь включите кластер pm2, лимит расползётся; зафиксируй это в комментарии.

**Критерий приёмки.** Холодный старт гостя ≤ 6 обращений к API (мерить
`performance.getEntriesByType('resource')`), ни одного заведомо 403.

### Задача 2.5. Ассет-кэш отвязать от версии приложения 🟠

`ASSET_CACHE = ege-history-assets-${APP_VERSION}` (`service-worker.js:6`), а
`cleanupOldCaches()` сносит всё, что не в `CACHE_NAMES`. Картинки не менялись, но
при каждом бампе SW пользователи заново качают **41 МБ** (244 файла из
`offline-assets.json`). Бампов уже было 39.

**Что сделать.** Отдельная константа `ASSET_MANIFEST_VERSION`, меняющаяся только при
изменении состава ассетов; `cleanupOldCaches` не трогает ассет-кэш чужой версии
приложения. Заодно: 323 JPEG на 46 МБ, максимум 1.95 МБ на файл — перегнать в WebP
с фолбэком, это минус ~60% трафика для мобильной аудитории. Ассеты и код кэшируются
независимо, `service-worker.selftest.js` расширить проверкой этого инварианта.

### Задача 3.2. Остаточный баг оценивания того же класса, что чинили 26.07
